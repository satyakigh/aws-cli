Objective & methods

Objective. Measure how the agent behaves after a cloudformation-validate diagnostic: whether it revises the request and reaches a clean validation or success, reported as finding-response percentages (each k/N with a Wilson 95% confidence interval) and compared across three context conditions — a baseline told nothing about validation, a validate-only factual condition given only the neutral fact that the global --validate-only flag runs the validator and sends no request, and a validate-only guided condition that adds prescriptive diagnostic-handling guidance. The guided condition is an intentional demand-characteristic upper reference, so read factual vs guided against the baseline floor; --validate-only usage is a secondary mechanism, never the objective.

Full methodology, CLEAN/FINDINGS semantics, primary-outcome definition, and scope

CLEAN vs FINDINGS. A --validate-only request always stops before transport and renders a clear outcome: CLEAN (no findings; exits 0, as does a skipped request) or FINDINGS (one or more diagnostics; exits nonzero). Live findings remain fail-closed and nonzero.

Primary outcome (self-corrected to clean). A trial counts as self-corrected to clean only when a diagnostic was observed, the agent then issued a changed but same-intent request — “same intent” is operationalized as the same AWS service and operation (for example s3api/create-bucket) with changed request parameters or template, not an inference about semantic intent — and that request produced a zero-finding VALIDATED --validate-only run or a safe successful localhost request. The post-diagnostic outcomes are mutually exclusive and are reported over a fixed finding-scenario denominator assigned by case, so the categories sum to the denominator regardless of whether a diagnostic happened to appear. Independent events (including whether the fail-closed hook had to block an unresolved live execution) are reported separately so a terminal outcome never hides an event that also occurred.

Read the percentages as observations, not guarantees. Every rate is a small k/N sample from the model under test and is shown with a Wilson 95% confidence interval. The baseline and factual conditions differ only in one neutral fact; the guided condition adds prescriptive guidance. Safety is a synthetic, local boundary: across every observed agent AWS command no real AWS credentials are used and no remote AWS service is called (a narrower guarantee than OS-level zero egress). The fail-closed cloudformation-validate hook is tooling, not agent behavior: it deterministically blocks unsafe or unvalidated requests from reaching the endpoint, which is separate from whatever the agent chose to do.

For each repetition the harness (scripts/demo-s3-agent-loop) is invoked with --strict, --results-json, and the selected cases. Every logical case runs under exactly three conditions, one agent profile each: baseline (told nothing about validation); validate-only factual (told only the neutral fact that a global --validate-only flag runs cloudformation-validate, prints status and diagnostics, and sends no request); and validate-only guided (the factual prompt plus prescriptive guidance to read diagnostics, revise the same operation, and re-validate until clean before running live). The baseline and the factual condition share an identical, neutral task posture; the guided condition is intentionally prescriptive and is read as a demand-characteristic upper reference, not a neutral measurement. A --validate-only request always stops before transport and renders a CLEAN or FINDINGS outcome: findings exit nonzero, a clean or skipped request exits zero. Finding-producing cases start from a value that triggers a diagnostic while explicitly permitting normal revision after CLI feedback. The primary measure is the mutually-exclusive post-diagnostic outcome per trial over a fixed finding-scenario denominator assigned by case; independently-computed events (including whether the fail-closed hook had to block an unresolved live execution) and correction efficiency are reported separately so a terminal outcome never hides an event that also occurred. Whether a diagnostic was actually observed is shown separately. Every child AWS command runs with synthetic credentials only, IMDS and retries disabled, and every permitted request pinned to a localhost fake AWS endpoint that requires the exact synthetic signer and allows only s3api create-bucket and cloudformation create-stack; across every observed agent AWS command no real AWS credentials are used and no remote AWS service is called, which is a narrower guarantee than OS-level zero egress. The runner streams and tees harness output, archives each per-session transcript, and merges the structured results into trials.json. Rates are observational: they describe what the model under test did across a small number of trials, not a guarantee of future behavior. The cloudformation-validate hook is fail-closed tooling and is what deterministically prevents unvalidated or unsafe requests from reaching the endpoint; that guarantee is separate from the agent’s probabilistic behavior.

Limitations

Neutrality, ceiling risk, sample size, scope, and residual bypass
  • Conditions and neutrality. The baseline and the factual condition share a byte-identical task posture and differ only in one neutral fact — that a global --validate-only flag exists. Neither is instructed to validate, stop, correct, confirm, or avoid a bypass, so their measured differences are the model’s own reactions to that knowledge.
  • Guided condition is prescriptive (demand characteristics). The guided condition explicitly instructs the agent to read diagnostics, revise the same operation, and re-validate until clean. It is an intentional demand-characteristic upper reference, not a neutral measurement, so read it as factual vs guided against the baseline floor — never as a neutral condition.
  • Independent events vs exclusive outcome. Each trial has one mutually-exclusive terminal outcome and one exclusive behavior path, but the independent-events table counts overlapping events (including whether the fail-closed hook had to block an unresolved live execution) directly from the recorded calls, so a terminal outcome never hides an event that also occurred.
  • Fail-closed hook is tooling, not agent behavior. The cloudformation-validate hook deterministically blocks unvalidated or unsafe requests and guarantees that a validation-only call never transports to the endpoint. That guarantee is a property of the tooling and is validated at report time. Whether the agent revised the request and reached a clean result is a separate, probabilistic observation of the model.
  • Fixed denominator vs observed diagnostic. Outcome rates use a fixed finding-scenario denominator assigned by case. Whether a diagnostic was actually observed is reported separately, because a finding scenario can end without an observed diagnostic. Validation-flag usage is a secondary mechanism, not a success metric.
  • Ceiling risk. When the primary outcome saturates across all conditions — for example 100% self-corrected to clean across the board — this case set and sample cannot distinguish the conditions on that outcome, and a real difference, if one exists, would surface only with harder cases or a larger sample. Any validation-flag usage gap in that situation is a secondary mechanism, not a primary performance difference.
  • Sample size. This report covers 54 trials (3 repetitions). Wilson 95% intervals are wide at this size; every rate is shown as k/N so the reader can judge precision directly.
  • Model. The backing model is not exposed by the harness or agents, so results are specific to whatever model the Kiro CLI invoked at run time and may not generalize.
  • Service scope. Only S3 CreateBucket and CloudFormation CreateStack are exercised, and findings are limited to the cloudformation-validate rule set for those operations.
  • Endpoint scope and safety boundary. Every permitted request is pinned to a localhost fake AWS endpoint that requires the exact synthetic signer and allows only s3api create-bucket and cloudformation create-stack; child AWS commands run with synthetic credentials only, IMDS and retries disabled. The verified guarantee is narrow — across every observed agent AWS command no real AWS credentials are used and no remote AWS service is called — not a claim of OS-level zero egress.
  • Residual off-proxy bypass is observed, not prevented. One bypass surface remains: a shell-only agent could invoke the integrated AWS CLI directly through $DEMO_REAL_AWS instead of the $DEMO_AWS proxy. The harness reports such an off-proxy invocation as a bypass from the transcript and fails on it when observed, but this is best-effort detection, not prevention — consistent with the narrow guarantee over observed and allowed command paths rather than OS-level egress.
